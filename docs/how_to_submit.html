How to submit, exactly

Executive summary › how to submit: the exact file, the exact commands, the exact clicks, and the gates this checkout passes right now.

A subpage of the executive summary. This is the recipe, in order: which file goes to the platform, five ways to obtain it (one of them this page itself, in your browser, with nothing installed; one of them a workflow you can fire from the repository page; one of them a CPU-only classifier that needs neither a GPU nor any artefact a runner produced), how to check it, where to click, and what the rules require of the upload. Every gate below is a measurement from this checkout; nothing here is typed from memory. The long-form page, submission details, carries the same procedure with the measurements and the irregularities in full.

What this file is and is not. It is the adopted artifact's prediction, bit-for-bit, in a container your browser wrote — so it passes the format gate, and it is the same field whose surrogate scores are on results. It is not a competition score: nothing in this repository can know how the platform's hidden new-fault labels will score it, and a file built here is only worth uploading after the validation step below is run on the bytes you actually hold.

5. Validate before uploading (the gate that catches a silent format break)

python scripts/validate_submission.py --pred submission.tif     --sample data/sample_submission.tif --train data/training_features.tif

Expected last line: ✅ Validation PASSED - Ready for submission! It checks CRS, resolution, single band, dtype, value range, grid, transform and NaN coverage, and exits non-zero on any failure, so it can gate a script. On the committed artifact the same log contains:

Check
✓CRS EPSG:32611
✓Resolution 100m
✓Single band
✓Dtype float32
✓Values in [0,1] (min 0.0000 max 1.0000)
✓Size matches sample 3292x3730
✓Transform matches sample
✓Size matches training_features
iNaN fraction 57.93% (NaN is expected outside the GeoDAWN footprint)
The sample file is a format template, not a prediction. The problem page calls it "a sample submission that predicts total fault absence" — the measured bytes disagree: sample_submission.tif carries 60,988 pixels at exactly 1.0, pixel-for-pixel the training labels (verified against the placed rasters in this checkout; see Data: Irregularity). It is correct to validate against it (grid, CRS, dtype); it is not an absence prediction, and uploading it would mean submitting the public catalogue as if it were your model.

5.1 If you would rather hand over a .zip

Both containers are accepted by the dialog; only one of them is described in the rules PDF, so the script writes the archive and then reads it back rather than trusting itself:

python scripts/package_submission.py --tif submission.tif --out submission.zip --json
python scripts/package_submission.py --tif submission.tif --out submission.zip --check

What the second command re-proves on the bytes you are about to upload: the archive holds one member named submission.tif, it is stored (the raster is already compressed, so nothing re-encodes your prediction), its bytes equal the .tif you validated, and GDAL can read it once extracted. The Build button in section 3 writes the same container with the same fixed archive timestamp, so the CLI route and the browser route are interchangeable — and the packager is re-packaged once to show it is deterministic.

7. After the upload

  • Record the sha256 you uploaded next to the leaderboard score the platform returns: that is the only unbiased number this project has ever had (every local number is a surrogate, on results).
  • Diarise the final selection. Deadline as recorded in docs/data_catalog.csv row C1: Dec 3 2026 11:59pm UTC — verified 2026-09-12 by fetch_page (VERIFIED - full text retrieved) from the competition home page. Confirm it on the platform: the catalogue is a dated snapshot, not a live feed.
  • Two official times exist, and they differ: the platform closes at 11:59 PM UTC (competition home page, verified 2026-09-21), while rules §A.1 separately requires the submission form / final content to be posted by 5:00 PM ET on the deadline date — for Dec 3 2026 that is 22:00 UTC, two hours earlier. The rules' §1.2 defers key dates to the competition website, so confirm both on the platform; acting on the earlier time (5:00 PM ET) is the safe reading. (§A.1 verified verbatim against the official rules PDF, full document read; see the sources page for the citation log.)
  • The same file is re-scored in Phase 2 against the expert-revised new-fault set.

    “Submissions will be reevaluated against the full, revised new fault dataset using the same distance-weighted Tversky index.”

9. The CPU route, and its own caveat

A submission that scores badly is still information; a submission that is never uploaded is not. Route C exists so a valid entry is possible from any machine in the project, and its own report refuses to claim competitiveness. Route A is the artifact to upload first.
